# 프로젝트 작업 지침

- 제품 범위는 [PRD](docs/product/PRD.md), 동작과 인수 기준은 [요구사항](docs/product/REQUIREMENTS.md)을 기준으로 삼는다. 빈 항목이나 미결정 사항을 확정된 요구사항으로 취급하지 않는다.
- 구현 전 영향을 받는 요구사항 ID와 검증 방법을 확인한다. 제품 방향을 바꾸는 결정과, 승인된 ADR을 바꾸거나 대체하는 주요 기술 선택은 담당자와 확인한다. 승인된 ADR 범위 안의 선택은 추천안으로 진행하고 기록하며 필요한 경우 [결정 기록](docs/decisions/README.md)을 남긴다. 사람이 반드시 개입해야 하는 경우와 추천안 자동 진행 규칙은 [오케스트레이션 절차](.claude/skills/orchestrate/SKILL.md)의 "필수 개입" 목록을 따른다.
- Mac 로컬 환경과 저장소 기준 상대 경로를 사용한다. 토큰, 기기 식별자, 서명 파일, 개인별 환경 설정은 저장소 밖에서 관리한다.
- 구현을 마친 뒤 관련 검사를 실행하고, 결과와 실행하지 못한 항목을 남긴다. 동작을 바꿨다면 가능한 경우 해당 사용자 흐름을 실제로 재현하고 확인한 환경을 명시한다.
- 커밋·이슈·PR은 [작성 규칙](docs/development/PR-ISSUE-GUIDE.md)을 따른다. 제목은 `feat: 로그인 화면 추가`처럼 영문 유형과 한국어 요약을 쓰고, 본문은 한국어로 쓴다. 이슈와 PR은 `.github/`의 템플릿을 채운다. `orca/` 작업 브랜치 푸시와 Draft PR 생성은 자동으로 진행한다. 두 독립 리뷰와 CI를 통과한 최종 커밋은 오케스트레이션 절차에 따라 병합한다. 이슈 생성과 배포에는 별도 승인이 필요하다.
- 독립 리뷰는 구현자의 요약과 함께 실제 diff, 인수 기준, 테스트 증거를 확인한다. [리뷰 기준](REVIEW.md)과 [개발 흐름](docs/development/WORKFLOW.md)을 따른다.

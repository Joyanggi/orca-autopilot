# 커밋·이슈·PR 작성 규칙

에이전트가 작업 PR을 올리고 검증과 두 리뷰 결과를 기록합니다. 일반 변경은 필수 검사를 통과하면 자동 병합하고, 사람 결정이 필요한 변경은 PR에서 확인합니다. 그래서 **사람이 위에서부터 30초 안에 상태를 파악하고, 필요한 곳만 더 읽는 구조**로 씁니다. 양식은 `.github/`의 템플릿이 기준입니다.

| 양식 | 파일 | 언제 |
| --- | --- | --- |
| PR | [pull_request_template.md](../../.github/pull_request_template.md) | 모든 PR |
| 작업 Issue | [task.md](../../.github/ISSUE_TEMPLATE/task.md) | 요구사항 구현, 문서 작업 |
| 버그 Issue | [bug.md](../../.github/ISSUE_TEMPLATE/bug.md) | 기대와 다른 동작 |
| 결정 요청 Issue | [decision.md](../../.github/ISSUE_TEMPLATE/decision.md) | 게이트: 사람이 정해야 하는 결정 |

## 커밋·PR 제목

제목은 `<유형>: <한국어 변경 요약>`으로 씁니다. 범위가 구분에 도움이 될 때는 `fix(auth): 토큰 만료 처리 수정`처럼 영문 범위를 추가합니다. 명령어, 파일명, 제품명, 요구사항 ID는 원문을 유지합니다. 제목은 한 줄로 쓰고 변경 대상과 행동을 드러냅니다.

| 유형 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 사용자 기능 추가 | `feat: 로그인 화면 추가` |
| `fix` | 잘못된 동작 수정 | `fix: 네트워크 끊김 시 저장 재시도 복구` |
| `docs` | 문서 추가·수정 | `docs: 마스터 시작 방법 정리` |
| `refactor` | 동작을 유지하는 구조 개선 | `refactor: 목록 정렬 로직 분리` |
| `perf` | 성능 개선 | `perf: 목록 조회 쿼리 개선` |
| `test` | 테스트 추가·수정 | `test: 입력 길이 경계값 검증 추가` |
| `style` | 코드 서식 정리 | `style: 설정 모듈 들여쓰기 정리` |
| `build` | 빌드 도구·의존성 변경 | `build: 빌드 의존성 갱신` |
| `ci` | CI 변경 | `ci: PR 제목 형식 검사 추가` |
| `chore` | 저장소 유지보수 | `chore: 저장소 작업 양식 정비` |
| `revert` | 앞선 변경 되돌리기 | `revert: 로그인 화면 변경 되돌리기` |

- **커밋**은 변경 단위별로 씁니다. 본문은 빈 줄 뒤에 배경과 이유를 한국어로 적고, 검증 결과는 기존 `Verified:` 줄에 실제 명령과 결과를 남깁니다. 관련 이슈는 필요할 때 `Refs #12`로 연결합니다.
- **PR**은 전체 변경의 대표 유형을 씁니다. 요구사항이 있으면 `feat: [F-040] 로그인 화면 추가`처럼 유형 뒤에 대표 ID를 적고, 나머지는 본문의 관련 항목에 적습니다. GitHub의 squash 커밋은 이 PR 제목을 사용합니다.
- **하위 호환성을 깨는 변경**은 유형 또는 범위 뒤에 `!`를 붙이고, 커밋 또는 PR 본문에 `BREAKING CHANGE:`와 영향·이전 방법을 기록합니다. 사람 승인 여부는 기존 개발 절차에 따릅니다.
- **검사**에서 PR 제목과 PR에 새로 들어오는 일반 커밋 제목의 유형·한국어 포함 여부를 확인합니다. 이슈와 PR 본문은 템플릿을 작성하는 에이전트가 이 규칙으로 점검합니다.

## 누가 쓰는가

- **개발 작업자**는 변경 커밋을 작성합니다. **마스터**는 제목을 확인한 뒤 `worker_done` 보고와 독립 리뷰 결과로 한국어 PR을 작성합니다.
- 개발 작업자는 보고에 PR 재료를 담습니다: 변경 요약, 검증 결과(명령·결과·환경), 실행하지 못한 검사와 이유, 커밋 해시, `Verified:` 줄.
- **`orca/` 작업 브랜치 푸시와 Draft PR은 자동**으로 올립니다. 외부 Issue는 사용자가 승인한 경우에만 올립니다.

## 작성 규칙

1. **템플릿의 섹션을 지우지 않습니다.** 해당 없으면 `해당 없음 — 이유`를 적습니다. 안내용 HTML 주석(`<!-- -->`)은 최종 본문에서 제거합니다.
2. **"30초 요약"을 먼저 채웁니다.** 상태(병합 가능 / 조건부 병합 / 보류), 사람이 결정할 것, 위험도를 한눈에 보이게 씁니다.
3. **사실과 추정을 구분합니다.** 확인하지 못한 것은 `미확인`으로 적고, 통과했다고 쓸 때는 명령과 결과를 함께 적습니다.
4. **한국어로, 짧게.** 한 항목은 1~3문장입니다. 비교는 표를 씁니다. 긴 로그는 핵심 20줄 이내만 넣고 나머지는 링크합니다.
5. **이슈 제목**은 `[작업] F-040 로그인 화면 추가`, `[버그] F-041 네트워크 끊김 후 저장이 되지 않음`, `[결정] 비밀번호 재설정을 첫 버전에 넣을까요?`처럼 씁니다. 요구사항과 연결되는 이슈만 ID를 붙입니다.
6. **붙이지 않는 것**: 키·토큰·`.env` 값, 정확한 위치 좌표, 이메일 등 개인정보, 사용자 식별자. 화면 증거는 개인정보를 가려 첨부합니다.

## 자동으로 정한 결정

선택지가 있고 추천안이 있으면 에이전트는 묻지 않고 추천안으로 진행합니다(사람이 꼭 개입해야 하는 목록은 [오케스트레이션 절차](../../.claude/skills/orchestrate/SKILL.md) 참고). 그 결정은 PR의 "자동으로 정한 결정" 표에 **결정, 고려한 선택지, 추천 이유, 되돌리는 방법**으로 모두 적어서 사람이 나중에 검토하고 뒤집을 수 있게 합니다. 없으면 "없음"이라고 씁니다.

## 상태 판정 기준

| 상태 | 조건 |
| --- | --- |
| 병합 가능 | 관련 P0 인수 기준 충족, PR 마지막 커밋에 두 리뷰의 PASS와 필수 CI 통과, 미해결 중요 지적 없음. 이견 재검토가 있었다면 같은 SHA의 재검토 판정 두 건을 사용 |
| 조건부 병합 | 남은 조건이 **사람의 행동만으로 해소**됨(예: 실기기 확인, 승인). 조건을 "30초 요약"에 명시 |
| 보류 | 코드·문서 수정이나 재리뷰가 필요함: 인수 기준 미충족, 중요 지적 미해결, 리뷰 커밋 불일치 |

## 위험도 기준

| 위험도 | 기준 | 사람 승인 |
| --- | --- | --- |
| 낮음 | 일반 문서(판정 기준 문서 제외), 내부 리팩터, 자동 검사 통과, 앱 동작 불변 | 요약 확인 |
| 중간 | 앱 동작·화면 변경 | 검증 결과와 리뷰 요약 확인 |
| 높음 | 인증·권한·개인정보 정책 변경, 운영 데이터 이전이나 삭제, 비용 발생, 사용자 요구사항 약화, 하네스·필수 CI·판정 기준 변경(요구사항·품질 체크·ADR) | **병합 전 사람 승인 필수**, 되돌리는 방법 명시 |

## Issue 작성

- PR이 이슈를 해결하면 관련 항목에 `Closes #12`를 씁니다. 일부만 처리하거나 참고하는 이슈는 `Refs #12`로 연결합니다.
- **작업**: 요구사항 ID, 포함/제외 범위, 시작 조건·행동·결과가 보이는 인수 기준을 적습니다. 완료 정의에 검증과 독립 리뷰를 넣습니다.
- **버그**: 재현 순서와 기대/실제 결과, 기기·OS·빌드를 적고 영향이 데이터 손실이나 권한 노출이면 "높음"으로 표시합니다.
- **결정 요청**: 질문은 한 가지, 선택지는 3개 이하, **추천과 이유를 반드시** 적습니다. 결정을 기다리는 작업과 기본값(결정하지 않을 경우)을 쓰고, 결정이 나면 사람이 "결정 결과"를 기록한 뒤 필요한 ADR을 갱신합니다.

## 에이전트 자체 점검

커밋·PR·이슈를 올리기 전에 확인합니다.

- [ ] 제목의 유형·접두사와 한국어 요약이 변경 목적을 보여준다
- [ ] "30초 요약"만 읽어도 병합 여부와 필요한 결정을 알 수 있다
- [ ] 모든 섹션이 채워져 있거나 `해당 없음 — 이유`가 있다
- [ ] 검증 결과에 실제 실행한 명령과 결과가 있고 미실행 항목이 분리돼 있다
- [ ] 독립 리뷰가 검토한 커밋 해시가 PR의 마지막 커밋과 같다
- [ ] 비밀값·개인정보가 없다
